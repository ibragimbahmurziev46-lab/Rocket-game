## 1. Краткое резюме

**Public Schedule** — это информационное табло расписания занятий колледжа, оформленное в стиле аэропортового
табло (split-flap display, «перекидные» ячейки). Табло рассчитано на вывод на большой экран/телевизор в
коридоре или холле учебного заведения.

Ключевая идея:

- данные о парах не вводятся вручную, а **загружаются из внешнего API NewLXP** (`https://api.newlxp.ru/graphql`);
- бэкенд на FastAPI периодически (каждые 5 минут) забирает расписание на диапазон «прошлая — текущая — следующая неделя»,
  нормализует его и складывает в локальный JSON-кэш;
- фронтенд на React раз в 10 секунд запрашивает расписание на выбранную дату и отображает его
  с анимацией «переворота» каждой буквы;
- для отладки предусмотрены URL-параметры `mockDate` и `mockTime`, а также встроенный редактор времени.

Проект состоит из двух независимых приложений (backend и frontend), которые запускаются параллельно и
связываются по HTTP через `http://localhost:8000/api/schedule`.

Уникальные особенности реализации:

- **Анимация split-flap сделана «с нуля»** на CSS 3D-трансформациях (`rotateX`) и React-таймерах, без сторонних библиотек.
- **Синхронизация переворота с часами**: переворот запускается каждые 10 секунд ровно тогда, когда
  `seconds % 10 === 0`, а строки переворачиваются каскадом (задержка на индекс строки).
- **Отсечение «отгоревших» пар**: пары, начавшиеся более 10 минут назад, скрываются — строка «уезжает» вверх,
  на её место поднимается следующая.
- **Экран-заставка**: если пар нет, вместо пустой таблицы рисуется ASCII-логотип из тех же перекидных ячеек.
- **Встраиваемый Python** (`backend/python_embed`) — проект можно запустить без установки Python в систему.

## 3. Архитектура и поток данных

```
 ┌──────────────────────┐        GraphQL (HTTPS)        ┌────────────────────────────┐
 │   NewLXP API         │ ◀───────────────────────────  │  backend/update_cache.py   │
 │ api.newlxp.ru/graphql│                               │  (разовый ручной запуск)   │
 │  - signIn            │                               └─────────────┬──────────────┘
 │  - curatorGroups     │                                             │ пишет
 │  - classesForStudent │                                             ▼
 │      Profile         │                               ┌────────────────────────────┐
 └──────────┬───────────┘                               │ backend/students_cache.json│
            │                                           │  группа → [id студентов]   │
            │ GraphQL (HTTPS)                           └─────────────┬──────────────┘
            ▼                                                           │ читает
 ┌──────────────────────────────────────┐                              │
 │ backend/main.py  (FastAPI, :8000)     │ ◀────────────────────────────┘
 │                                      │
 │  startup → фоновый поток:            │        пишет/читает
 │    каждые 5 мин fetch_week_from_api()├──────────────▶ backend/week_schedule.json
 │        3-недельный диапазон          │               { "YYYY-MM-DD": [уроки] }
 │  GET /api/schedule?date=YYYY-MM-DD   │
 │        отдаёт день из памяти         │
 └───────────────┬──────────────────────┘
                 │ JSON  {"schedule": [...], "is_empty": bool}
                 ▼
 ┌──────────────────────────────────────┐
 │ frontend (React + TS, Vite, :5173)   │
 │  fetch каждые 10 с → рендер табло    │
 │  split-flap анимация, часы, дата     │
 └──────────────────────────────────────┘
```

Особенности взаимодействия:

1. **Фронтенд никогда не обращается к NewLXP напрямую** — все обращения к внешнему API инкапсулированы в бэкенде.
2. **Фронтенд не хранит состояние на сервере** — выбранная дата живёт только в состоянии компонента `App`
   и передаётся как query-параметр `?date=`.
3. **Бэкенд — «read-only» для фронтенда**: единственный публичный эндпоинт `GET /api/schedule`.
4. **Данные всегда доступны офлайн** (после первого успешного обновления), так как `week_schedule.json`
   читается с диска при старте сервера.
5. Если внешнее API недоступно, табло продолжает работать на последнем успешном кэше; в консоль бэкенда
   печатаются сообщения об ошибках.

### 5.2. `launch.bat` (48 строк)

Автоматический запуск всего проекта в Windows. Логика:

1. `title` / `color 0A` — зелёное окно.
2. **Проверка структуры**: наличие `backend\python_embed\python.exe` и `frontend\node_modules`.
   Если чего-то нет — `[ERROR]` и `pause`/`exit`.
3. Запуск бэкенда в отдельном окне:
   `start "Schedule Backend" cmd /k "cd backend && python_embed\python.exe -m uvicorn main:app --reload --port 8000"`
   - используется **встроенный Python** (`python_embed`), а не `venv`;
   - включён `--reload` (автоперезапуск при изменении кода);
   - порт `8000`.
4. Запуск фронтенда в отдельном окне:
   `start "Schedule Frontend" cmd /k "cd frontend && npm run dev"` → Vite на `http://localhost:5173`.
5. `timeout /t 5` — пауза на инициализацию серверов.
6. `start http://localhost:5173` — открытие браузера.
7. Финальное сообщение и пауза 3 секунды.

Практические следствия: `launch.bat` **требует уже установленных** `frontend/node_modules` (то есть
`npm install` нужно выполнить один раз заранее) и рассчитан на запуск из корневой папки проекта.

### 5.3. `update_cache.bat` (24 строки)

Обёртка для `backend/update_cache.py`:

1. `cd /d "%~dp0"` — переход в папку, где лежит скрипт (работает и при запуске двойным кликом).
2. Если существует `backend\venv\Scripts\python.exe` — используется он («Using virtual environment...»).
3. Иначе — глобальный `python backend\update_cache.py`.
4. `pause` в конце, чтобы окно не закрылось и пользователь увидел результат.

Замечание: `launch.bat` использует `python_embed`, а `update_cache.bat` — `venv`/глобальный Python.
То есть в проекте сосуществуют **два разных Python-окружения**, и зависимости должны быть установлены
в том, которое реально будет использоваться.

## 6. Папка `backend/`

Назначение: серверная часть. Содержит FastAPI-приложение, скрипт обновления справочника студентов,
два JSON-кэша и два Python-окружения.

### 6.1. `backend/main.py` (277 строк, ~9,5 КБ)

Единственный рабочий сервер приложения. Структурно делится на: конфигурацию → вспомогательные функции →
фоновое обновление → HTTP-эндпоинт.

#### Конфигурация и константы

| Имя | Значение / смысл |
|-----|------------------|
| `GRAPHQL_URL` | `https://api.newlxp.ru/graphql` — единственный внешний эндпоинт |
| `ORGANIZATION_ID` | `04329772-ff8b-4123-a65b-298e1fa799fb` — ID организации (в `main.py` объявлен, но **не используется**) |
| `BASE_DIR` | абсолютный путь к папке `backend` (через `__file__`) |
| `CACHE_FILE` | `backend/students_cache.json` |
| `WEEK_CACHE_FILE` | `backend/week_schedule.json` |
| `ACCOUNT` | e-mail и пароль служебного аккаунта NewLXP (в открытом виде) |
| `ROOM_TRANSLATIONS` | словарь аудиторий: `ЛИССАБОН→LISBON`, `АФИНЫ/АФИНЬ→ATHENS`, `ЛОНДОН→LONDON`, `ПАРИЖ→PARIS`, `МАДРИД→MADRID`, `РИМ→ROME`, `БЕРЛИН→BERLIN`, `ТОКИО→TOKYO`, `ДУБАЙ→DUBAI`, `СТОКГОЛЬМ→STOCKHOLM`, `НЬЮ-ЙОРК→NEW YORK`, `ВЕНА→VIENNA`, `МЕХИКО→MEXICO`, `СИДНЕЙ→SYDNEY`, `ДУБЛИН→DUBLIN`, `КАИР→CARIO` |
| `_cached_token` | кэш Bearer-токена (в памяти процесса) |
| `_session` | singleton `requests.Session` |
| `_students_cache` / `_last_cache_mtime` | кэш справочника групп + mtime файла |
| `_weekly_schedule_cache` | расписание в памяти: `{ "YYYY-MM-DD": [урок, ...] }` |
| `_cache_lock` | `threading.Lock` для доступа к `_weekly_schedule_cache` |

Также задан CORS-middleware: `allow_origins=["*"]`, `allow_methods=["*"]`, `allow_headers=["*"]` — открыто для всех.

#### `clean_and_translate_room(raw_name)`

1. Если имя пустое → `"—"`.
2. Регуляркой `\s*\(\d+\)$` **удаляется числовой суффикс в скобках** (например, `ЛИССАБОН (2)` → `ЛИССАБОН`).
3. Поиск в `ROOM_TRANSLATIONS` по верхнему регистру; если перевода нет — возвращается исходное имя.

Следствие: аудитории, пришедшие из API уже латиницей («Hong Kong», «Dubai»), остаются как есть,
а кириллические названия становятся англоязычными — так табло выглядит однородно.

#### `get_session()`

Создаёт и кэширует `requests.Session` с параметрами:

- `trust_env = False` — **игнорируются системные прокси и переменные окружения** (важно для машин за прокси);
- политика ретраев `Retry(total=3, backoff_factor=1, status_forcelist=[429,500,502,503,504])`;
- адаптер монтируется и для `https://`, и для `http://`;
- заголовки, имитирующие браузер: `User-Agent` (Chrome/Windows), `Content-Type: application/json`,
  `Origin: https://newlxp.ru`, `Referer: https://newlxp.ru/`.

#### `get_access_token()`

Выполняет GraphQL-запрос авторизации:

```graphql
query SignIn($input: SignInInput!) { signIn(input: $input) { accessToken } }
```

- при наличии `errors` в ответе бросается `Exception("Ошибка авторизации: ...")`;
- токен сохраняется в `_cached_token` и **переиспользуется до перезапуска процесса**
  (обновления по истечении срока действия нет, повторный `signIn` при 401 не выполняется);
- таймаут запроса — 90 секунд.

#### `load_all_groups_to_cache()`

Читает `students_cache.json` с «умным» кэшированием по `mtime`:

- если файла нет → печатает `=== CACHE FILE NOT FOUND ===` и возвращает `{}`;
- если кэш в памяти актуален (`current_mtime == _last_cache_mtime`) → возвращает его без чтения диска;
- иначе читает файл, печатает `=== LOADING GROUPS FROM LOCAL FILE ===` и `=== GROUPS LOADED: N ===`;
- любое исключение перехватывается, печатается `=== ERROR READING FILE: ... ===`, возвращается `{}`.

Именно эта функция фигурирует в README как место «зависания», если файл заблокирован другим процессом.

---
#### `fetch_week_from_api()`

Основная «тяжёлая» функция (выполняется в фоновом потоке):

1. Считает диапазон: понедельник **прошлой** недели → воскресенье **следующей** (21 день):
   `monday = today - timedelta(days=today.weekday() + 7)`, `sunday = monday + timedelta(days=20)`.
2. Загружает справочник групп; если он пуст — выходит.
3. Получает токен, формирует заголовки `Authorization: Bearer ...` и `apollographql-client-name: web`.
4. Для каждой группы берёт **первых двух студентов** (`student_ids[:2]`) — компромисс между полнотой
   и скоростью: расписание группы у всех студентов одинаковое, но API отдаёт его только по студенту.
5. Для каждого студента выполняет GraphQL-запрос:

```graphql
query ManyClassesForStudentProfileSchedule($input: ClassesForStudentProfileInput!) {
  classesForStudentProfile(input: $input) {
    id
    from
    learningGroup { name __typename }
    classroom { name __typename }
    __typename
  }
}
```

с переменными `{ studentId, from: date_from, to: date_to }`, таймаут 45 с, пауза `time.sleep(0.2)` между запросами.

6. Собирает уникальные занятия в словарь по `id` (дедупликация: два студента одной группы
   возвращают одни и те же пары).
7. Нормализует каждое занятие в компактный объект:

```json
{ "id": "uuid", "group": "1Д1", "start_time": "2026-11-16T06:15:00.000Z", "room": "DUBLIN" }
```

   - `group` = `learningGroup.name.split('-')[0]` (из `1Д1-9.26` получается `1Д1`);
   - `room` = `clean_and_translate_room(...)`;
   - записи без аудитории или без группы **отбрасываются** (когда значение `—`).

8. Группирует по дате `from[:10]` (UTC-дата) и сортирует занятия внутри дня по `start_time`.
9. Пишет результат в `week_schedule.json` (`ensure_ascii=False`, `indent=4`) и подменяет
   `_weekly_schedule_cache` под `_cache_lock`.

#### `background_updater()`

- при старте, если `week_schedule.json` существует, **сразу загружает его в память** → табло работает
  мгновенно после перезапуска, ещё до первого обращения к API;
- далее бесконечный цикл: `fetch_week_from_api()` → `time.sleep(300)` (5 минут);
- исключения ловятся и печатаются как `Критическая ошибка в фоновом потоке: ...`, поток не умирает.

#### Точка входа и эндпоинт

```python
@app.on_event("startup")
def startup_event():
    threading.Thread(target=background_updater, daemon=True).start()

@app.get("/api/schedule")
def get_schedule(date: str = None):
    target_date = date if date else datetime.now().strftime("%Y-%m-%d")
    with _cache_lock:
        schedule = _weekly_schedule_cache.get(target_date, [])
    return {"schedule": schedule, "is_empty": len(schedule) == 0}
```

- поток `daemon=True` → завершается вместе с процессом;
- `GET /api/schedule` — единственный эндпоинт, параметр `date` опционален (по умолчанию «сегодня»);
- ответ **всегда** `200 OK`; отсутствие данных выражается `schedule: []`, `is_empty: true`;
- блок `if __name__ == "__main__"` позволяет запускать `python main.py` (uvicorn на `0.0.0.0:8000`);
- используется устаревший `@app.on_event("startup")` (в актуальных версиях FastAPI рекомендован `lifespan`).

### 6.2. `backend/update_cache.py` (152 строки, ~5,6 КБ)

Разовый консольный скрипт, наполняющий `students_cache.json`. Запускается вручную через `update_cache.bat`.

Алгоритм `main()`:

1. Создаёт `requests.Session` с `trust_env = False` и теми же «браузерными» заголовками, что и `main.py`.
2. **Авторизация** (`signIn`) → токен; при ошибке — сообщение и `sys.exit(1)`.
3. Запрашивает у API группы куратора:

```graphql
query GetCuratorGroups($input: CuratorGroupsInput!) {
  curatorGroups(input: $input) {
    items { name isArchived students { id __typename } __typename }
    __typename
  }
}
```

4. Делает **16 поисковых запросов** по комбинациям «курс + специальность»:
   `1Д, 1П, 1ИБ, 1Р, 2Д, 2П, 2ИБ, 2Р, 3Д, 3П, 3ИБ, 3Р, 4Д, 4П, 4ИБ, 4Р`
   (параметры `organizationId` + `search`), таймаут 120 с, пауза 0,5 с между запросами.
   Причина перебора — эндпоинт `curatorGroups` не отдаёт всё сразу / ломается при пустом поиске.
5. Для каждой группы применяет **двойной фильтр устаревших групп**:
   - `isArchived` от сервера;
   - собственная эвристика `is_group_active(name)`.
6. Сохраняет результат `{ "имя группы": ["id студента", ...] }` в `students_cache.json`.
7. Печатает итог: путь к файлу, количество групп и список имён.

Функция `is_group_active(group_name)`:

- разбирает имя вида `1Д1-9.26`: часть до дефиса (курс + код) и часть после дефиса (`9.26`);
- `course = int(parts[0][0])` — первая цифра = курс;
- `year_suffix = int(parts[1].split('.')[1])` — последние две цифры года набора (`26` → 2026);
- `admission_year = 2000 + year_suffix`;
- группа активна, если `admission_year + course >= current_year - 1`;
- при любой ошибке разбора возвращает `True` (группа не отсеивается).

**Важный дефект:** импортированы `json, requests, sys, time, os`, но **не импортирован `datetime`**,
хотя он используется внутри `is_group_active` (`datetime.now().year`). Возникает `NameError`, который
перехватывается голым `except:`, после чего функция возвращает `True`. То есть математический фильтр
**фактически не работает**, и отсев архивных групп опирается только на флаг `isArchived` от сервера.
Ошибка «тихая»: скрипт не падает, но задуманная логика не выполняется.

#### Эффекты (жизненный цикл)

1. **resize** — обновляет `windowHeight`.
2. **Автоскролл** — каждые 60 секунд плавно прокручивает `board-body` вверх (`scrollTo({top:0, behavior:'smooth'})`),
   чтобы табло не «уезжало» вниз при большом числе строк.
3. **Первый переворот** — через 50 мс после монтирования `flipTrigger` становится `1`
   (до этого анимация отключена, чтобы не «перекидывать» пустой экран).
4. **visibilitychange** — при возврате фокуса на вкладку выполняется переворот (актуализация после сна/сворачивания).
5. **Часы** — интервал 1 с:
   - в обычном режиме `setCurrentTime(new Date())`;
   - в mock-режиме время инкрементируется на 1 секунду от предыдущего значения;
   - когда `seconds % 10 === 0`, вызывается `setFlipTrigger(t => t + 1)` — так переворот синхронизирован с часами.
6. **Загрузка расписания** — `fetch(`${API_URL}?date=${dateString}`)` сразу и далее каждые 10 секунд;
   ошибки только логируются в консоль, интерфейс продолжает работать на старых данных.

---
#### Логика «снимка» и фильтрации

Ключевой приём: табло не перерисовывается в момент прихода данных, а **фиксирует снимок** на момент переворота.

```ts
useEffect(() => {
  setSnapshotTime(timeRef.current);
  setSnapshotLessons(lessonsRef.current);
}, [flipTrigger, lessons]);
```

Далее `displayedLessons` (через `useMemo`):

1. Если просматривается **не сегодняшний** день (`isToday === false`) — показываются все занятия дня.
2. Если **сегодня** — занятие остаётся, только если с момента начала прошло меньше `EXPIRE_MINUTES` (10 минут):
   `diff = (snapshotTime - start) / 60000; return diff < EXPIRE_MINUTES`.
   То есть пара исчезает спустя 10 минут после начала, а не после окончания.
3. Сортировка по `start_time` по возрастанию.

`rowCount` **только увеличивается** (`if (displayedLessons.length > rowCount) setRowCount(...)`) —
при уменьшении числа пар на экране остаются пустые строки и табло не «прыгает».

`rows` — массив длины `rowCount`, где отсутствующие занятия заменены на `null` (пустая строка табло).

#### Заставка (ASCII-логотип)

Когда `displayedLessons.length === 0`, вместо строк рисуется логотип из двух «слов» (верхнее — `ITHUB`,
подсвечено фиолетовым акцентом). Логотип — массив строк из символов `█` и пробелов:

- `logoRows` (useMemo) рассчитывает вертикальные отступы так, чтобы блок был **вертикально центрирован**
  по фактической высоте экрана: `cellHeightVw = 3.5`, `rowGapVw = 0.15`, `headerHeightPx = 16 * pixelsPerVw`;
- горизонтальное центрирование — `paddingLeft = floor((TOTAL_COLS - maxLength) / 2)`;
- каждая строка добивается пробелами до `TOTAL_COLS`, чтобы сетка ячеек была ровной;
- `visibleShowLogo` переключается **в середине** переворота (`FLIP_DURATION_MS / 2`), поэтому смена
  «таблица ↔ логотип» происходит в момент, когда ячейки уже перевёрнуты — визуально бесшовно.

---
#### Компонент `MemoizedFlipRow`

`memo(({ lesson, currentTime, flipTrigger, index }) => ...)`:

- `IntersectionObserver` (threshold 0.1) определяет, видна ли строка на экране (`isRowVisible`);
  невидимые строки **не анимируются** — экономия ресурсов при большом числе пар;
- `visibleTime` обновляется **в середине** переворота строки, с задержкой `index * ROW_STAGGER_MS + 300 мс`;
- при `lesson === null` рендерится пустая строка (`forceEmpty` во всех колонках);
- статус: `start = new Date(lesson.start_time)`, `end = start + 80 минут`;
  `isOngoing = visibleTime >= start && visibleTime <= end` → в колонке «Статус» выводится `ИДЕТ`.

**Важно:** длительность пары 80 минут зашита прямо в компоненте (`80 * 60000`) — это отмечено
в README как известное ограничение.

#### Компонент `FlipText`

`memo(...)` — раскладывает строку на символы:

- `padded = text.padEnd(length, ' ').slice(0, length)` — дополняет пробелами и обрезает по длине колонки;
- при `forceEmpty` — строка целиком из пробелов;
- каждому символу передаётся `absoluteCharIndex = charOffset + i` (общий индекс в строке),
  что даёт сквозной каскад «волны» по всем четырём колонкам.

#### Компонент `FlipChar` (ядро анимации)

`memo(...)`, состояние: `currentChar` (что видно на нижней половине), `nextChar` (что придёт на верхнюю),
`isFlipping` (запущен ли CSS-переворот).

Логика эффекта:

1. Если `flipTrigger === 0` **или** строка не видна — мгновенно выставить оба символа в целевой (без анимации).
2. Если и текущий, и целевой символы — пробел, ничего не делать (не тратить таймеры на пустоту).
3. Иначе три таймера:
   - `startTimer` (через `totalDelay`): `setNextChar(target)`, `isFlipping = true` — начинается анимация;
   - `swapTimer` (через `totalDelay + 300 мс`): `setCurrentChar(target)` — в середине переворота
     нижняя половина получает новый символ;
   - `endTimer` (через `totalDelay + 600 мс`): `isFlipping = false`.
4. `totalDelay = rowIndex * ROW_STAGGER_MS + absoluteCharIndex * CHAR_STAGGER_MS` — волна слева направо
   и сверху вниз.

Разметка одной ячейки — четыре половины (классическая схема split-flap):

| Слой | Класс | Что показывает |
|------|-------|----------------|
| статичная верхняя | `half top-static` | **новый** символ (`nextChar`) |
| статичная нижняя | `half bottom-static` | **старый** символ (`currentChar`) |

## 8. Контракт API и доменные алгоритмы

### 8.1. `GET /api/schedule`

| Параметр | Тип | Обязателен | Описание |
|----------|-----|-----------|----------|
| `date` | string `YYYY-MM-DD` | нет | дата, на которую нужно расписание; по умолчанию — сегодня |

Пример запроса и ответа:

```
GET http://localhost:8000/api/schedule?date=2026-11-24
```

```json
{
  "schedule": [
    {
      "id": "20f7ffb7-...",
      "group": "4Д1",
      "start_time": "2026-11-24T06:00:00.000Z",
      "room": "Hong Kong"
    }
  ],
  "is_empty": false
}
```

Гарантии:

- HTTP `200` в любом случае (в том числе для неизвестной даты — тогда `schedule: []`, `is_empty: true`);
- поле `is_empty` **не используется** фронтендом (он проверяет `displayedLessons.length`),
  но полезно для отладки и внешних потребителей;
- CORS открыт, так что эндпоинт можно вызывать из браузера с любого origin.

### 8.2. Алгоритм «актуальности» строки на табло

```
для каждой пары: start = Date(start_time), diff = (now - start) / 60000
сегодня:  показывать, если diff < 10
не сегодня: показывать всегда
```

Следствия для эксплуатации:

- пара исчезает с табло через 10 минут после начала, независимо от её длительности;
- на табло остаются **все будущие пары** и пары, начавшиеся менее 10 минут назад;
- при пустом результате включается заставка с логотипом.

### 8.3. Алгоритм статуса `ИДЕТ`

```
end = start + 80 минут
ИДЕТ, если start <= visibleTime <= end
```

`visibleTime` — «замороженное» на момент переворота время, поэтому статус не «мигает» между кадрами,
а меняется вместе со следующим переворотом (не чаще, чем раз в 10 секунд).

### 8.4. Алгоритм обновления данных

| Кто | Что делает | Период |
|-----|-----------|--------|
| `background_updater` (backend) | `fetch_week_from_api()` — 23 группы × 2 студента × 21 день | 300 с (5 мин) |
| `App` (frontend) | `fetch('/api/schedule?date=...')` | 10 с |
| `App` (frontend) | `setFlipTrigger` при `seconds % 10 === 0` | 10 с |
| `App` (frontend) | плавный скролл `board-body` в начало | 60 с |
| Ручное | `?date=` + кнопки ◀/▶ | по нажатию |

Итого за один цикл бэкенд делает ~46 GraphQL-запросов (по 2 студента на 23 группы) с паузами 0,2 с,
то есть обновление занимает ориентировочно 10–60 секунд и полностью выполняется в фоновом потоке,
не блокируя `GET /api/schedule`.

## 10. Наблюдения, риски и технический долг

### 10.1. Функциональные дефекты

| № | Где | Проблема | Влияние |
|---|-----|----------|---------|
| 1 | `backend/update_cache.py` | не импортирован `datetime`, но используется в `is_group_active`; `NameError` глушится голым `except:` → функция всегда возвращает `True` | фильтр устаревших групп по году набора **не работает**; отсев идёт только по `isArchived` |

| 3 | `frontend/src/App.tsx` | `TOTAL_COLS = 31` (5+5+16+5), а в CSS ширины `5+6+14+5 = 30` ячеек | возможное несовпадение сетки логотипа и колонок, обрезка длинных аудиторий |

### 10.2. Риски безопасности и сопровождения

1. **Учётные данные в открытом виде.** Логин и пароль (`ACCOUNT`) прописаны и в `main.py`, и в `update_cache.py`,
   а также хранятся в git-истории. При публикации репозитория пароль нужно сменить и вынести в переменные
   окружения/`.env` (последний уже в `.gitignore`).
2. **Открытый CORS (`allow_origins=["*"]`)** — любой сайт может обращаться к `/api/schedule`.
   Для локального табло это допустимо, для публичного размещения — нет.
3. **Токен без обновления.** `_cached_token` живёт до перезапуска процесса; при истечении токена
   обновление расписания начнёт молча падать с ошибками API до рестарта.
4. **`trust_env = False`** — сознательный отказ от системных прокси; в сети, где выход только через прокси,
   запросы к NewLXP работать не будут.
5. **`python_embed/` в git** — тысячи файлов `site-packages` в индексе: тяжёлый клон, шум в истории,
   риск конфликтов при обновлении пакетов. Логичнее хранить как артефакт/архив или игнорировать.

### 10.3. Хрупкость данных и логики

- **Расписание берётся только по первым двум студентам группы.** Если у этих студентов нет пары,
  которую посещает группа (подгруппы, индивидуальные занятия), пара не попадёт на табло.
- **Записи без аудитории отбрасываются** (`—`) — дистанционные занятия и пары без кабинета
  не отображаются вообще.
- **Ключ группировки — UTC-дата** (`from[:10]`), а фронтенд фильтрует по локальной дате.
  Для пар поздно вечером/рано утром (смещение UTC+3) возможен сдвиг дня.
- **Длительность пары 80 минут зашита** — при другой сетке звонков статус `ИДЕТ` будет неверным.
- **Словарь аудиторий статичен** — новые кириллические названия будут отображаться по-русски,
  пока их не добавят в `ROOM_TRANSLATIONS`.
- **`rowCount` не уменьшается** — после дня с большим числом пар на экране остаётся много пустых строк
  (осознанный компромисс против «прыгающего» табло).
- **`fetch` без проверки `response.ok`** — при ошибке 500 бэкенда `response.json()` может бросить исключение;
  оно попадёт в `catch`, данные останутся прежними (деградация мягкая, но причина видна только в консоли).
- **Жёсткий `API_URL = 'http://localhost:8000'`** — если открыть табло с другого компьютера
  (например, с телевизора в коридоре), запросы уйдут на `localhost` этого телевизора и не сработают.
  Нужно либо `server.proxy` в Vite, либо конфигурируемый адрес.
- **Один компонент на всё приложение** (`App.tsx`, 531 строка) — при росте функциональности
  файл станет трудно поддерживать; уместно выделить `Clock`, `DateNav`, `Board`, `FlipCell` в отдельные модули.

### Как проект работает в двух предложениях

Бэкенд на FastAPI в фоновом потоке раз в 5 минут забирает из GraphQL-API NewLXP расписание на три недели
по всем группам (используя справочник ID студентов) и складывает нормализованные пары в JSON-кэш,
отдавая их затем по `GET /api/schedule?date=...`. Фронтенд на React раз в 10 секунд забирает день
и рисует его «перекидными» ячейками: будущие пары и пары, начавшиеся менее 10 минут назад, со статусом
`ИДЕТ` для текущей пары, с заставкой-логотипом при отсутствии занятий.
